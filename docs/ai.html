AI Architecture & Prompts

How TherapOS assembles patient context, routes to AI models, and generates clinical content. Every prompt template, behavioral rule, and memory strategy documented here — copy-paste ready.

⚠
Design vs. current build (25 Oct 2026)

This page describes the target design. The current code calls OpenAI GPT-4o for every task (note drafts, prep, homework, summaries) with the model ID hard-coded, and sends the patient's full name in the prompt. Before launch: move model IDs to environment variables, decide the provider split (Claude for drafts and summaries is the documented plan), and pseudonymise identifiers before every model call. Verify model IDs against each provider's current model list; IDs shown below may be outdated. Prompt caching only applies once Anthropic models are actually used.

Model Routing

Different tasks get different models, chosen for cost and quality tradeoffs:

TaskModelOutputWhy
SOAP/DAP note draftsClaude Sonnet (latest)SSE streaming textBest nuanced clinical writing, strong instruction following, streams reliably
Session prep briefGPT-4oJSON (structured)Reliable enforced JSON via response_format, fast response
Homework suggestionsGPT-4oJSON (structured)Structured JSON, creative but grounded, good at modality-specific thinking
Patient summary refreshClaude Haiku (latest)Plain textFast, low-cost, excellent summarization — runs after every finalized note
Note embeddingstext-embedding-3-smallvector(1536)$0.02/1M tokens, 1536 dimensions, excellent semantic quality

ℹ
Model versioning

Model IDs are configured in environment variables (ANTHROPIC_MODEL, OPENAI_MODEL). Never hardcode model IDs in business logic. When a new Claude or GPT version releases, update the env var and test before deploying — model behavior can change between versions.

Context Assembly Pipeline

Every AI call starts by assembling a PatientContext object. This is the most important function in the codebase — what goes in determines what comes out. Bad context = bad notes, regardless of how good the model is.

// apps/api/src/ai/context.service.ts
async buildPatientContext(
  patientId: string,
  sessionId?: string
): Promise<PatientContext> {
  const [patient, goals, recentSessions, latestHomework] = await Promise.all([
    this.prisma.patient.findUniqueOrThrow({
      where: { id: patientId },
      select: {
        firstName: true, preferredName: true,
        primaryConcerns: true, diagnoses: true,
        modality: true, aiSummary: true,
      }
    }),
    this.prisma.goal.findMany({
      where: { patientId, status: 'ACTIVE' },
      orderBy: { createdAt: 'asc' },
      select: { title: true, description: true, category: true, status: true }
    }),
    this.prisma.session.findMany({
      where: { patientId, status: 'COMPLETED' },
      include: {
        note: {
          select: {
            format: true, subjective: true, objective: true,
            assessment: true, plan: true,
            data: true, dapAssessment: true, dapPlan: true,
            freeText: true, finalizedAt: true,
          }
        }
      },
      orderBy: { scheduledAt: 'desc' },
      take: 5,  // Last 5 sessions only — budget constraint
    }),
    this.prisma.homework.findMany({
      where: { patientId },
      orderBy: { createdAt: 'desc' },
      take: 3,  // Last 3 homework items
      select: { title: true, status: true, category: true, createdAt: true }
    }),
  ])

  return {
    patient: {
      firstName: patient.preferredName || patient.firstName,
      modality: patient.modality,
      concerns: patient.primaryConcerns,
      diagnoses: patient.diagnoses,
      aiSummary: patient.aiSummary,
    },
    goals: goals.map(g => ({
      title: g.title,
      category: g.category,
      status: g.status,
    })),
    recentSessions: recentSessions.map(s => ({
      sessionNumber: s.sessionNumber,
      date: s.scheduledAt,
      note: this.truncateNote(s.note, 400),  // Hard limit per note
    })),
    latestHomework: latestHomework.map(h => ({
      title: h.title,
      status: h.status,
      category: h.category,
    })),
  }
}

private truncateNote(note: SessionNote | null, maxTokens: number): string {
  if (!note) return ''
  // Concatenate all non-null fields with labels
  const parts = [
    note.subjective && `S: ${note.subjective}`,
    note.objective  && `O: ${note.objective}`,
    note.assessment && `A: ${note.assessment}`,
    note.plan       && `P: ${note.plan}`,
    note.freeText   && note.freeText,
  ].filter(Boolean).join('\n')
  // Rough token estimate: 1 token ≈ 4 chars
  return parts.slice(0, maxTokens * 4)
}

Context Window Budget

Context pieceMax tokensStrategyWhy this limit
System prompt~500Fixed per task typeConstant — doesn't scale with patient history
Patient profile + concerns + diagnoses~200Always included in fullSmall, high-value — always needed
Rolling AI summary~300Always included in fullThis IS the memory layer — never truncate it
Active treatment goals~200All active goals includedGoals shape every clinical decision — always include
Last 3–5 session notes~2,000400 tokens per note maxRecency is more valuable than completeness
Recent homework (last 3)~200Title + status onlyLow-token, high-relevance for continuity
Therapist raw notes (this session)~2,000Included in fullThis is the primary signal — never truncate
Total~5,400Well within Claude's 200k and GPT-4o's 128k limits

The budget is conservative by design. Claude Sonnet supports 200k tokens — we use 5k. The reason: prompt caching. Anthropic's prompt cache TTL means frequently-used patient summaries and static system prompts are cached and not re-billed. Keeping prompts short and stable maximizes cache hit rate.

Prompt Templates

Template 1 — Session Prep Brief

Used for: POST /ai/prep/:sessionId. Model: GPT-4o with response_format: { type: "json_object" }.

You are an AI assistant helping a licensed {modality} therapist prepare for a session. You are NOT a therapist. You are a preparation tool only. Never diagnose. Never prescribe. Never make clinical decisions. THERAPIST CONTEXT: Modality: {modality} | License type: {licenseType} PATIENT: {firstName} | Session #{sessionNumber} Primary concerns: {concerns} Active diagnoses (context only, do not reference in output): {diagnoses} ROLLING AI SUMMARY (what the AI understands about this patient so far): {aiSummary} ACTIVE TREATMENT GOALS: {goals} LAST {n} SESSIONS (newest first, context for continuity): {recentSessionNotes} LAST ASSIGNED HOMEWORK: Title: {hwTitle} | Status: {hwStatus} | Category: {hwCategory} Generate a concise session preparation brief for the therapist to read in 90 seconds. Return EXACTLY this JSON structure (no other text): { "recap": "2-3 sentence summary of what happened last session and key themes. Write as if briefing a colleague.", "suggestedQuestions": ["Question 1", "Question 2", "Question 3", "Question 4"], "homeworkFollowUp": "One sentence on how to approach checking in on the homework assignment.", "patterns": "One sentence describing a notable cross-session pattern, or null if none is evident." } RULES: - Questions MUST match the therapist's modality (CBT questions for CBT, psychodynamic for psychodynamic, etc.) - Be concise — therapist reads this in 90 seconds before walking into the room - If information is missing or this is session 1, say so clearly rather than generating filler - Do not mention medication, diagnosis codes, or specific legal/ethical matters - Patterns must be observed across at least 2 sessions to be noted

Template 2 — SOAP Note Draft

Used for: POST /ai/note/draft (format=SOAP). Model: Claude Sonnet, SSE streaming.

You are an AI assistant helping a licensed therapist draft a SOAP progress note. This is a DRAFT for therapist review and editing. It is NOT a final clinical document. The therapist will review, edit, and finalize before it becomes part of the record. PATIENT: {firstName} | Session #{sessionNumber} | {date} MODALITY: {modality} PRIMARY CONCERNS: {concerns} PATIENT CONTEXT (recent history — use for continuity, not verbatim copying): Rolling summary: {aiSummary} Last sessions (for continuity): {recentSessionNotes} Active goals: {goals} Homework status: {homeworkStatus} THERAPIST'S RAW NOTES FROM THIS SESSION (primary source — trust this above all else): --- {rawNotes} --- Draft a professional SOAP progress note based ONLY on the therapist's raw notes above. The context sections are for continuity — do not add details from prior sessions unless directly relevant to what the therapist noted today. SOAP FORMAT DEFINITIONS: - Subjective: What the patient reported — their words, feelings, experiences - Objective: Therapist's direct observations — affect, presentation, engagement, behavior - Assessment: Clinical synthesis — themes, progress toward goals, session arc - Plan: Next steps — homework, next session focus, any referrals or follow-up STRICT RULES: 1. Use ONLY information present in the therapist's raw notes 2. If a field cannot be written from the raw notes, write "[Therapist to complete]" 3. Do not fabricate quotes, events, clinical observations, or patient statements 4. Keep each section to 2-4 sentences — clinical notes are concise 5. Do not include diagnosis codes 6. Do not mention AI or the note generation process in the note text 7. Write in third person ("The patient reported..." not "Maya reported...") 8. Clinical language appropriate to the modality is encouraged Return JSON: {"subjective":"...","objective":"...","assessment":"...","plan":"..."}

Template 3 — DAP Note Draft

Used for: POST /ai/note/draft (format=DAP). Model: Claude Sonnet, SSE streaming.

You are an AI assistant helping a licensed therapist draft a DAP progress note. This is a DRAFT for therapist review. Not a final clinical document. PATIENT: {firstName} | Session #{sessionNumber} | {date} MODALITY: {modality} | CONCERNS: {concerns} CONTEXT (for continuity): {context} THERAPIST'S RAW NOTES: --- {rawNotes} --- DAP FORMAT DEFINITIONS: - Data: Observable information — what was reported, what was observed, events discussed - Assessment: Clinical interpretation — what the data means for the treatment arc - Plan: Concrete next steps RULES: Same as SOAP — use only raw notes, no fabrication, write "[Therapist to complete]" for gaps. Return JSON: {"data":"...","dapAssessment":"...","dapPlan":"..."}

Template 4 — Homework Suggestions

Used for: POST /ai/homework/suggest. Model: GPT-4o with JSON mode.

You are helping a {modality} therapist generate homework assignments for a patient. You are a tool — not a therapist. The therapist selects and approves all homework. PATIENT: {firstName} THERAPEUTIC MODALITY: {modality} PRIMARY CONCERNS: {concerns} TODAY'S SESSION THEMES (from therapist's raw notes): {sessionThemes} ACTIVE TREATMENT GOALS: {goals} PREVIOUSLY ASSIGNED HOMEWORK (for variety — avoid repeating recent assignments): {previousHomework} Generate 3 distinct homework options. Each must be: - Concrete and immediately actionable by the patient - Appropriate to the stated therapeutic modality - Grounded in today's session themes - Different in category from the other two options Return EXACTLY this JSON (no other text): { "options": [ { "title": "Short name for the assignment (5-8 words)", "description": "Detailed patient-facing instructions — what to do, when, how often. 3-5 sentences.", "category": "journaling|behavioral|exposure|mindfulness|social|psychoeducation", "rationale": "One sentence explaining why this fits the session themes and modality." }, { ... }, { ... } ] } RULES: - Do not suggest medication, diagnosis, or clinical interventions requiring a license - Homework must be completable independently by the patient between sessions - Exposure homework should be graduated — never jump to the feared stimulus directly - CBT: favor thought records, behavioral experiments, activity scheduling - DBT: favor diary cards, skills practice, chain analysis - Psychodynamic: favor journaling, dream logs, relationship reflection - ACT: favor values clarification, defusion exercises, committed action tracking

Template 5 — Patient Summary Refresh

Used by: refresh-summary BullMQ job (after every note finalization). Model: Claude Haiku.

You are updating a rolling clinical summary for a therapist's internal reference. This summary helps the AI prepare better session briefs and note drafts. It is NOT part of the official clinical record — it is a tool for the AI, reviewed by the therapist. PATIENT: {firstName} | Total sessions completed: {sessionCount} PREVIOUS SUMMARY (written after session {prevSessionNum}): {previousSummary} NEWEST FINALIZED SESSION NOTE (Session #{sessionNumber}, {date}): {latestNote} Update the summary to reflect the newest session. The summary should capture the patient's overall treatment arc — not just the latest session. REQUIREMENTS: - 3-5 sentences maximum - Focus on: what has improved, what persists, recent breakthroughs or patterns, current clinical picture - Written for a therapist who knows this patient — not an external reader - Clinically accurate but not diagnostic — no DSM codes or diagnoses - If this is session 1, summarize the presenting picture only Return ONLY the updated summary text. No JSON wrapper. No preamble. No "Here is the summary:"

Memory Architecture (Three Tiers)

Tier 1 — Redis

What: Active session state. Session prep brief (cached 24h). In-progress note draft. Rate limit counters.

TTL: 24 hours for prep cache. Session-scoped for note drafts.

Used for: Zero-latency reads during live sessions. Not the source of truth — PostgreSQL is.

Tier 2 — PostgreSQL

What: Rolling 3–5 sentence AI summary per patient. Stored in Patient.aiSummary.

Update: After every note finalization, via refresh-summary BullMQ job.

Used for: Injected into every AI call — session prep, note draft, homework. The "working memory" of the system.

Tier 3 — pgvector

What: Every finalized note embedded as a 1536-dimensional vector. Stored in NoteEmbedding.

Update: After every note finalization, via embed-note BullMQ job.

Used for: Natural language search. Deep context retrieval for complex queries.

Embedding Pipeline Detail

// apps/api/src/jobs/embed-note.job.ts

async processEmbedNote(job: Job<{ noteId: string }>) {
  const note = await this.prisma.sessionNote.findUniqueOrThrow({
    where: { id: job.data.noteId },
    include: { session: true }
  })

  // Build text to embed — include all populated note fields
  const noteText = [
    note.subjective  && `Subjective: ${note.subjective}`,
    note.objective   && `Objective: ${note.objective}`,
    note.assessment  && `Assessment: ${note.assessment}`,
    note.plan        && `Plan: ${note.plan}`,
    note.data        && `Data: ${note.data}`,
    note.dapAssessment && `Assessment: ${note.dapAssessment}`,
    note.dapPlan     && `Plan: ${note.dapPlan}`,
    note.freeText    && note.freeText,
  ].filter(Boolean).join('\n')

  // Get embedding from OpenAI
  const response = await this.openai.embeddings.create({
    model: 'text-embedding-3-small',
    input: noteText,
  })
  const vector = response.data[0].embedding  // float[1536]

  // Upsert — handles re-embedding if note is edited after initial embedding
  await this.prisma.$executeRaw`
    INSERT INTO "NoteEmbedding" (id, "noteId", "patientId", "therapistId", content, embedding, "createdAt")
    VALUES (${cuid()}, ${note.id}, ${note.session.patientId}, ${note.session.therapistId},
            ${noteText}, ${vector}::vector, NOW())
    ON CONFLICT ("noteId") DO UPDATE
    SET content = EXCLUDED.content, embedding = EXCLUDED.embedding
  `
}

AI Behavioral Contract

These rules are enforced at the prompt level, not in application code. Every prompt template includes them. They cannot be overridden by user input.

RulePrompt enforcementConsequence if violated
Never diagnose"Never diagnose. No DSM codes in outputs."Clinical liability. Therapist edits the note regardless.
Never fabricate"Use ONLY information from raw notes. Missing = [Therapist to complete]."False clinical record. This is the highest-risk failure mode.
Always a draftSystem prompt labels all output as "DRAFT for review"False sense of authority. UI reinforces this with ✦ badge.
No medication"Do not suggest medication or prescriptions"Out of scope. Regulatory risk.
Modality-awareTherapist modality injected in every promptIrrelevant or wrong suggestions.
Risk nudge onlySeparate application-layer check, not in promptSee below — soft nudge, never a clinical alarm.

Risk Nudge Implementation

The risk nudge is NOT done by AI prompt — it's done by a keyword pattern match in the application layer, applied to finalized note text before the response is sent to the client. If specific terms are detected (suicidal ideation, homicidal ideation, self-harm, specific plan or means references), a soft callout is returned alongside the note:

// apps/api/src/notes/notes.service.ts (post-finalization check)

const RISK_PATTERNS = [
  /suicid/i, /self.harm/i, /hurt.*self/i, /homicid/i,
  /want to die/i, /end.*(my|their|his|her) life/i,
  /specific plan/i, /means.*access/i,
]

function checkRiskPatterns(noteText: string): boolean {
  return RISK_PATTERNS.some(pattern => pattern.test(noteText))
}

// If true, the API response includes:
// "riskNudge": "This note may contain content warranting a safety assessment review."
// This is displayed as a soft callout in the UI — not an alarm, not required action.

The nudge is informational only. It does not block finalization, does not send any alert, and does not create a mandatory action. The therapist is a licensed professional who has already read and edited this note — the nudge is a safety net, not a clinical decision.

Error Handling in AI Calls

AI calls can fail for several reasons. The system handles each gracefully:

Error typeBehaviorUser sees
AI provider 5xx (outage)BullMQ retries 3x with exponential backoff"Generation failed. Try again." Raw notes are saved.
Rate limit (provider 429)Retry after Retry-After headerBrief delay, then auto-retry
Invalid JSON from modelRetry once with "return valid JSON" emphasisTransparent to user if retry succeeds
JSON retry also failsReturn error to client"Generation failed. Try again." Raw notes saved.
Context too large (edge case)Truncate oldest session notes firstNote quality may be lower — not shown to user
Network timeoutSSE stream closes, client detects disconnect"Connection lost. Retry generation."
✓
Raw notes are always saved first

Before any AI call, the therapist's raw notes are saved to the database. If AI generation fails entirely, the therapist still has their raw notes. They can try again, or use the raw notes as the basis for a manual note. AI failure is never data loss.

Prompt Engineering Principles

  1. Role first, scope second, rules last. Every prompt starts with the AI's role and what it is NOT. Then defines the task. Rules come at the end where they're most recently primed.
  2. Explicit format enforcement. JSON output prompts always specify the exact structure, field names, and types. Ambiguity in format = inconsistent parsing = user-facing bugs.
  3. Placeholder naming. All dynamic values use {camelCase} placeholders that match the PatientContext field names. No magic strings.
  4. Modality injection. The therapist's modality is injected into every prompt. CBT therapists get CBT-appropriate questions and homework. This is not optional — it's the core value differentiation.
  5. No hallucination escape hatch. The prompt explicitly defines what happens when information is missing: write "[Therapist to complete]". There is no room for the model to be helpful by guessing.
  6. Test prompts with adversarial inputs. Before deploying a prompt change, test it with raw notes that are: very short (2 words), very long (1000 words), first session (no prior context), and emotionally intense (crisis content). The prompt must handle all gracefully.
