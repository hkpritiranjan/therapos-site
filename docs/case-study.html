Case Study: Building TherapOS

The TherapOS story so far: the problem, what research changed, the key decisions, what was built in the first four days, what broke, and what is still unproven.

⚠
Status: pre-launch, no customers yet

This case study documents what has been decided and built, and what is still unproven. It contains no customer results because there are no users yet. Sections marked "to be filled" will be completed with beta data. Last updated 25 October 2026.

At a glance

The product

An AI documentation and patient-memory tool for independent therapists. It sits beside the therapist's EHR and does not record sessions.

The build

Turborepo monorepo: NestJS API, Next.js app, Prisma on Postgres with pgvector. 38 TypeScript files, about 5,700 lines, 9 commits over 4 days (21–24 Jul 2026).

The state

Core loop works locally: patient → session → raw notes → AI draft → edit → finalize → memory. Production login, compliance and billing are not built.

1. The problem

Independent therapists run a one-person clinical practice. After each session they write a progress note, and before the next one they try to remember what happened weeks ago. The tools they use were built for billing, not for clinical continuity: an EHR stores notes but does not help recall them, and a blank SOAP template starts from zero every time.

AI scribes now address the writing half. APA's 2025 survey shows the share of psychologists who have never used AI at work fell from 71% to 44% in a year, and use is mostly administrative (Research §3). But most of those tools want to record the session, which raises consent, retention and psychotherapy-notes questions that many clinicians are uncomfortable with. About nine in ten psychologists report concerns about AI.

The gap we chose: notes and memory for the therapist who does not want a recording tool in the room.

3. What the research changed

The original plan assumed a feature gap: "no competitor combines AI notes, session prep and cross-session memory." A competitor review in October 2026 found that was wrong. Upheal, Mentalyc and SimplePractice all advertise cross-session features. Pricing was also off: Eleos is an enterprise product, not a $200 solo plan, and TherapyNotes and Upheal cost more or less than we had written.

Two things survived scrutiny and now carry the strategy:

  1. Text-first. No audio is recorded. That avoids recording consent, transcript retention and most of the psychotherapy-notes ambiguity, and it is a clear trust story in a market where SimplePractice began defaulting new users into de-identified transcript retention in June 2026.
  2. EHR-agnostic memory. Competitor AI that ships inside an EHR is locked to it. A therapist who already uses SimplePractice or TherapyNotes can add TherapOS with no migration.

The full evidence, with confidence tags, is on the Research page.

5. How it works

  1. Prepare

    Before a session the therapist opens a prep brief built from goals, the last five completed sessions (note text truncated to a token budget), and recent homework: key topics, interventions to consider, goals to review, and homework to follow up.

  2. Capture

    During or after the session they type raw notes into the session page. Nothing is recorded.

  3. Draft

    The draft endpoint streams a structured note in the chosen format. The system prompt forbids fabrication and diagnosis, requires "[Therapist to complete]" for gaps, and uses neutral third-person clinical language.

  4. Edit and finalize

    The therapist edits every field and finalizes. Finalized notes cannot be edited.

  5. Remember

    Finalizing queues a background job: embed the note into pgvector, then regenerate the patient's rolling summary from the last ten finalized notes. The next prep brief starts from that memory.

Where the docs and code still disagree

  • Models: docs describe Claude for drafts and summaries; code uses GPT-4o everywhere with hard-coded IDs. Decision pending in §9.
  • Auth: docs describe Clerk with MFA; code uses its own JWT.
  • Response shapes: docs show data and meta; the API returns success, data, and top-level pagination fields.
  • Editor and UI kit: docs name Tiptap and shadcn/ui; the app uses plain inputs and Tailwind.

11. What we would do differently

  • Research before copy. The site was written before the competitor and regulatory review, and carried claims that did not survive it. Evidence first, marketing second.
  • Deploy on day one. Six of nine commits were deployment work, and most of the fixes were things a day-one empty-service deploy would have caught.
  • Keep docs and code in one place. The docs site and the app live in separate repos and drifted within days. A single "status" table, as in §7, should be updated in the same pull request as any behaviour change.
  • Do not over-promise compliance. "HIPAA-ready" and "BAAs signed" are statements a regulator or customer can hold you to. Say what is built.
